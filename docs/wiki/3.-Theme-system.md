# Theme system

Themes are discovered from folders in `resources/themes/`. Atom ships `atom` and `dusk`. The folder name is both the theme ID and its label; use lowercase letters, digits and single hyphens, starting with a letter. The IDs `all`, `core`, `housekeeping` and `vendor` are reserved. Each theme uses its own `theme-<id>::` namespace for views and components.

Installer and reset mail are explicit Core views under `resources/views/core`, outside the public theme requirements. Activating a theme (Housekeeping's CMS `theme` setting, the web installer, `atom:setup` or `atom:install --theme=<id>`) requires a valid installed theme folder, the 14 core views in `ThemeValidator::REQUIRED_VIEWS` and a usable build; otherwise the stored value stays unchanged and the reasons are shown. The minimum covers welcome/authentication, `user.me`, account/password/two-factor settings, banned/maintenance and Nitro. Other pages may be omitted without blocking activation. A page view the route requests that the theme omits returns 404. A view missing while a page renders (a layout, partial or Livewire view), an invalid definition or an unavailable essential build returns the 503 diagnostic. Omitting a template does not disable backend actions or change permissions. `atom:install` builds the theme before activating it; with `--skip-build` it activates a theme whose views are complete and leaves the build to you. `atom:themes:validate` without a theme ID fails on rejected folders only when one is the selected theme; other rejected folders are reported as warnings. Housekeeping, the installer, the API and payment callbacks remain independent. See the [installation and deployment guide](1.-Installing-Atom-CMS.md) for custom installer/mail override upgrade paths.

Themes only apply in full mode. In [headless mode](10.-Headless-mode.md) there is no public theme.

Build the target theme before changing the `theme` value through Housekeeping's CMS settings:

```bash
npm ci
npm run build:all
```

`build:all` builds both themes and the shared targets. To build one theme, use its build command and build Core and housekeeping separately. `php artisan build:theme` offers an interactive selection. During development use `npm run dev:atom` or `npm run dev:dusk`.

Theme outputs are independent: `public/build/themes/atom` and `public/build/themes/dusk`. `build:atom` and `build:dusk` build only their respective theme, preserving the other's output. `build:core` and `build:housekeeping` build shared outputs separately; `build:all` builds each target once. Development markers are `storage/vite/atom.hot` and `storage/vite/dusk.hot`; `npm run dev:core` and `npm run dev:housekeeping` use `storage/vite/core.hot` and `storage/vite/housekeeping.hot`.

To scaffold a custom theme:

```bash
php artisan make:theme my-theme
```

The command comes from the installed `qirolab/laravel-themer` package and only creates a starting directory: the result cannot be activated until it provides every required view and names its own components as `<x-theme-my-theme::…>`. Review its generated files and add the `dev:my-theme` and `build:my-theme` scripts it prints to `package.json`. Follow the shared [theme Vite configuration](../../resources/js/theme-vite.config.js) for asset paths and manifests. Decline replacement authentication scaffolding unless replacing that integration is intentional; Atom's existing authentication and controllers support the hotel's features.

Themes may use Core's shared, non-visual pieces instead of copying them: `<x-core::seo-meta />` for the page title and meta tags, `<x-core::fancybox-assets />` for the Fancybox scripts, `\App\Support\FlashToasts::from(session()->driver(), $errors)` for the flashed toast messages and `\App\Support\FooterCredits::contributors()` and `translators()` for the translated credits. Markup and styling stay in the theme.

In the theme's `vite.config.js`, import `createThemeConfig` from the shared [theme Vite configuration](../../resources/js/theme-vite.config.js) and export `createThemeConfig(__dirname)` to use `css/app.css` and `js/app.js` as inputs. These are the conventional entrypoints loaded by `theme_vite()` in development and production; import additional CSS and JS from them. A theme's `js/app.js` should register the shared shop component with `Alpine.data("packagePurchase", …)` from `resources/js/components/PackagePurchase.js` and then call `startPublicTheme()` from `resources/js/public-theme.js`, which sets up Axios, starts Livewire once, and adds the Flowbite and shop tooltip hooks. A valid folder makes the theme discoverable, but activation still requires its views and assets. Build the custom theme, run `php artisan atom:themes:validate my-theme --production`, set its ID as the CMS `theme` through Housekeeping, and check the login, registration, user settings, client, shop and housekeeping flows. Use the shared [settings guidance](README.md#changing-settings) when making database changes outside Housekeeping.

The asset check needs a readable `public/build/themes/<id>/manifest.json` with an entry for `css/app.css` and `js/app.js`. Outside production a development hot file satisfies it; in production a hot file is an error. For unavailable media, `theme_asset()` logs the missing asset and returns a URL in the selected theme's build directory so the browser can handle the missing file. Production deployments need compiled output and views, not original JS/CSS/media sources; building requires source entrypoints. `php artisan atom:mode --status` reports invalid themes as diagnostics and does not require public theme files in headless mode.
